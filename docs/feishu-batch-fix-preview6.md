# preview.6 飞书批量同步稳定性修复

## 问题与证据

在用户授予剪贴板权限后，实际 Chrome 批量上传暴露两个问题：

- 新建飞书文档被浏览器标记为仍在加载，旧逻辑等待整个标签页在 20 秒内加载完成；失败后观察到文档编辑器已可用。标签页整体加载状态不能准确代表编辑器是否准备好。
- 注入的剪贴板准备脚本发生 Promise 拒绝时，Chrome 未返回原始错误，仅得到“剪贴板准备失败”。补充结构化错误后，真实操作显示“回读剪贴板失败：Clipboard data has changed”，说明快照在读取期间失效。导致快照变化的具体应用或事件未确定，不将其归因于用户操作或某个其他扩展。

首轮两份文档中，第二份成功并通过刷新后的服务端回读；失败文档保留 URL，插件未自动重新创建它们。文档地址和本机日志仅保存在本地交付报告，不写入公开源码。

后续还实际确认目标 Chrome 窗口处于 `minimized` 状态，页面 `innerWidth/innerHeight` 为零。原来的坐标计算没有检查可见区域，因此原生粘贴可以返回已执行，但正文没有写入；服务端校验正确地判为失败。

## 修改

- 通过立即注入的只读检查确认当前文档 URL、DOM 状态和编辑器存在，以此判断是否准备好，不依赖所有第三方页面资源加载完成。等待上限 60 秒。
- 在写入之前完整备份支持的剪贴板格式；焦点拒绝仅短时间重试只读访问。
- 使用 Clipboard API 一次写入本地 HTML 和纯文本，避免 DOM copy 事件经过编辑器自身的处理程序。该处理程序是否造成首轮快照变化尚未证实。
- 快照失效时短时间重新读取，不重复写入。回读 HTML 仍需与准备的正文一致，之后才允许原生粘贴。
- 以数据返回注入异常，保留备份、写入、回读阶段以及具体错误，不再只报告缺少结果。原有剪贴板恢复、调试连接释放和服务端正文回验继续执行。
- 已创建但失败的文档继续禁止直接重试，避免重复创建。
- 编辑器和剪贴板操作前激活目标标签页及其窗口，最小化时恢复为普通窗口；计算粘贴坐标时只接受可见交集，粘贴前再次检查坐标在页面内。用户上传时需要浏览器保持可见。

## 验证范围

扩展 70/70 测试通过，新增覆盖剪贴板原始错误、焦点重试上限、不支持的格式、标签页仍加载但编辑器已准备好、快照失效后只重新读取且只写入一次、最小化目标窗口恢复。TypeScript 与 Vite 生产构建通过。

在用户已登录的 Chrome 154 中，安装的 preview.6 使用真实后台处理两份本地 Markdown，最终批次 2/2 成功，生成两份独立飞书文档。第一份包含 C 代码块、本地 PNG 和网站链接；第二份包含 Python 代码块和不同的网站链接。同步结束后分别重新加载两个文档，再独立读取服务端保存数据：两者均返回 HTTP 200、业务码 0、完整块数据，正文、代码和链接一致，第一份图片存在上传 token，第二份没有多出图片。此验证未替换同步消息或飞书网络请求。

测试文档地址、界面记录和脱敏回读结果保存在本地交付报告。目录路径导入另外在独立 Chromium 的授权目录选择流程验证；最终真实飞书批次使用多选文件入口，不将其混称为真实 Chrome 的路径选择验证。未扩大为大批量、其他租户或 OneNote 登录验证。

这些主机测试验证恢复与诊断逻辑，不代表所有网络、剪贴板管理软件或其他浏览器扩展都兼容。上传期间避免其他程序同时修改剪贴板；检测到正文不同会停止粘贴。
